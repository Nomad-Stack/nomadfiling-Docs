## Eine Authentifizierungsmethode wählen

Authentifiziere MCP-Anfragen entweder mit einem NomadFiling-API-Schlüssel oder einem OAuth-2.1-Zugriffstoken. Verwende API-Schlüssel für Server-zu-Server-Zugriff, den du direkt steuerst, und OAuth, wenn du einen Client baust, der Nutzer anmeldet und delegierten Zugriff benötigt.

<Callout kind="info">

`initialize`, `tools/list` und `ping` erfordern keine Authentifizierung. `tools/call` erfordert gültige Bearer-Anmeldedaten und gibt `401 Unauthorized` zurück, wenn die Authentifizierung fehlschlägt.

</Callout>

<Tabs>
  <Tab title="API-Schlüssel" icon="key">

Verwende einen API-Schlüssel, wenn dein MCP-Client in einer vertrauenswürdigen Umgebung läuft und du keinen Zustimmungsablauf für Endnutzer benötigst.

**Header-Format**

```http
Authorization: Bearer nf_4a6d3a58c8f0b21f6b4e9d0a7f3c1b2e5d6f7a8b9c0d1e2f3a4b5c6d7e8f901
```

**Serverprüfung**

- Prüft, dass das Token mit `nf_` beginnt
- Berechnet den SHA-256-Hash des Roh-Tokens
- Vergleicht diesen Hash mit `api_keys.key_hash`
- Prüft, dass die Zeile in `api_keys` existiert
- Prüft, dass `expires_at` entweder `null` oder in der Zukunft liegt
- Aktualisiert `api_keys.last_used_at` asynchron
- Gibt bei Erfolg `user_id` zurück, bei Fehler `null`

  </Tab>
  <Tab title="OAuth 2.1" icon="lock">

Verwende OAuth 2.1, wenn dein Client Nutzerautorisierung, Zustimmung und erneuerbare Zugriffstoken benötigt.

**Header-Format**

```http
Authorization: Bearer mcp_at_0SxQYxjC4gG2P7rZlN8vWmKb3uD5eHqTfA1pLs9nJcY
```

**Serverprüfung**

- Prüft, dass das Token mit `mcp_at_` beginnt
- Berechnet den SHA-256-Hash des Roh-Tokens
- Vergleicht diesen Hash mit `oauth_tokens.access_token_hash`
- Prüft, dass die Zeile in `oauth_tokens` existiert
- Prüft, dass `revoked` `false` ist
- Prüft, dass `expires_at` in der Zukunft liegt
- Aktualisiert `oauth_tokens.last_used_at` asynchron
- Gibt bei Erfolg `user_id` zurück, bei Fehler `null`

  </Tab>
</Tabs>

## Authentifizierte Anfragen senden

Übergib die Anmeldedaten im Header `Authorization` als Bearer-Token. Der MCP-Server akzeptiert dasselbe Header-Muster für beide Authentifizierungsmethoden.

<CodeGroup tabs="cURL,JavaScript,Python">
```bash
curl https://mcp.nomadfiling.com/tools/call \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer nf_4a6d3a58c8f0b21f6b4e9d0a7f3c1b2e5d6f7a8b9c0d1e2f3a4b5c6d7e8f901" \
  -d '{
    "jsonrpc": "2.0",
    "id": "req_7aK2mP",
    "method": "tools/call",
    "params": {
      "name": "get_filing_status",
      "arguments": {
        "filingId": "fil_9m2x8q1p"
      }
    }
  }'
```

```javascript
const response = await fetch("https://mcp.nomadfiling.com/tools/call", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": "Bearer nf_4a6d3a58c8f0b21f6b4e9d0a7f3c1b2e5d6f7a8b9c0d1e2f3a4b5c6d7e8f901"
  },
  body: JSON.stringify({
    jsonrpc: "2.0",
    id: "req_7aK2mP",
    method: "tools/call",
    params: {
      name: "get_filing_status",
      arguments: {
        filingId: "fil_9m2x8q1p"
      }
    }
  })
});

const data = await response.json();
console.log(data);
```

```python
import requests

response = requests.post(
    "https://mcp.nomadfiling.com/tools/call",
    headers={
        "Content-Type": "application/json",
        "Authorization": "Bearer nf_4a6d3a58c8f0b21f6b4e9d0a7f3c1b2e5d6f7a8b9c0d1e2f3a4b5c6d7e8f901",
    },
    json={
        "jsonrpc": "2.0",
        "id": "req_7aK2mP",
        "method": "tools/call",
        "params": {
            "name": "get_filing_status",
            "arguments": {
                "filingId": "fil_9m2x8q1p"
            }
        },
    },
)

print(response.json())
```
</CodeGroup>

Wenn die Authentifizierung erfolgreich ist, wird die Anfrage mit der authentifizierten `user_id` im Kontext an das ausgewählte Tool weitergeleitet. Wenn die Authentifizierung fehlschlägt und die Methode `tools/call` ist, gibt der Server eine Authentifizierungsaufforderung zurück.

<Request>
```http
POST /tools/call HTTP/1.1
Host: mcp.nomadfiling.com
Content-Type: application/json
Authorization: Bearer nf_invalid_token_value

{
  "jsonrpc": "2.0",
  "id": "req_unauth_01",
  "method": "tools/call",
  "params": {
    "name": "get_filing_status",
    "arguments": {
      "filingId": "fil_9m2x8q1p"
    }
  }
}
```
</Request>

<Response tabs="401">
```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="mcp", resource_metadata="https://mcp.nomadfiling.com/.well-known/oauth-protected-resource"
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "error": {
    "code": -32001,
    "message": "Unauthorized"
  },
  "id": "req_unauth_01"
}
```
</Response>

## Einen NomadFiling-API-Schlüssel verwenden

API-Schlüssel sind die einfachste Option für Backend-Dienste, Skripte und private Automatisierungen. Jeder Schlüssel wird einmal in der NomadFiling-App erstellt, und auf dem Server wird nur sein Hash gespeichert.

<Callout kind="alert">

Der Klartext-API-Schlüssel wird einmal angezeigt, wenn du ihn erstellst. Speichere ihn in deinem Secret Manager, bevor du den Erstellungsdialog verlässt.

</Callout>

### Einen API-Schlüssel erstellen

Erzeuge API-Schlüssel in der NomadFiling-App unter [/de/account/api-keys](/de/account/api-keys). Gib einen Namen für den Schlüssel ein, erzeuge ihn und kopiere den Klartextwert, bevor du den Dialog schließt.

Ein gültiger API-Schlüssel hat das Format `nf_`, gefolgt von 64 hexadezimalen Zeichen. Die vollständige Zeichenkette ist einschließlich Präfix 67 Zeichen lang.

```text
nf_4a6d3a58c8f0b21f6b4e9d0a7f3c1b2e5d6f7a8b9c0d1e2f3a4b5c6d7e8f901
```

### API-Schlüssel-Format und Validierung

<ParamField header="Authorization" param-type="string" required="true">
Bearer-Token in der Form `Bearer nf_...`. Der Server authentifiziert nur den Roh-Token-Wert nach dem Präfix `Bearer `.
</ParamField>

<ParamField body="token prefix" param-type="string" required="true" show-location="false">
Muss `nf_` sein.
</ParamField>

<ParamField body="raw token length" param-type="string" show-location="false">
32 Zufallsbytes, nach dem Präfix als 64 hexadezimale Zeichen kodiert.
</ParamField>

<ParamField body="stored value" param-type="string" show-location="false">
SHA-256-Hash des vollständigen Roh-Tokens, gespeichert in `api_keys.key_hash`.
</ParamField>

<ParamField body="expiry check" param-type="timestamp or null" show-location="false">
Die Authentifizierung gelingt nur, wenn `expires_at` `null` ist oder später als die aktuelle Zeit liegt.
</ParamField>

<ParamField body="usage tracking" param-type="timestamp" show-location="false">
Der Server aktualisiert `api_keys.last_used_at` nach erfolgreicher Authentifizierung asynchron.
</ParamField>

### Ergebnis der API-Schlüssel-Authentifizierung

<ResponseField name="user_id" field-type="string" required="true">
Nutzerkennung, die der passenden Zeile in `api_keys` zugeordnet ist.
</ResponseField>

Wenn die Validierung fehlschlägt, gibt der API-Schlüssel-Authenticator `null` zurück. Für `tools/call` schlägt die Anfrage dann mit der zuvor gezeigten Antwort `401 Unauthorized` fehl.

## OAuth 2.1 mit PKCE verwenden

OAuth 2.1 ergänzt Client-Registrierung, Nutzerzustimmung, kurzlebige Zugriffstoken und rotierende Refresh-Token. NomadFiling unterstützt den Authorization-Code-Grant und den Refresh-Token-Grant.

<Callout kind="tip">

Verwende PKCE für jeden öffentlichen Client. Der Server unterstützt sowohl `S256` als auch `plain`, aber `S256` ist die sicherere Wahl.

</Callout>

### OAuth-Endpunkte

| Endpunkt | Methode | Zweck |
| --- | --- | --- |
| `/register` | `POST` | Einen OAuth-Client registrieren |
| `/authorize` | `GET` | Den Autorisierungsablauf starten |
| `/approve` | `POST` | Nach Nutzerfreigabe einen Autorisierungscode erstellen |
| `/token` | `POST` | Einen Autorisierungscode oder ein Refresh-Token eintauschen |

### Vollständiger OAuth-Ablauf

<Steps>
  <Step title="Registriere deinen Client" icon="plus">

Sende eine Anfrage an `/register` mit mindestens einer Redirect-URI. Der Server erstellt eine Client-ID mit dem Präfix `mcp_client_` und bei Bedarf ein Client-Secret mit dem Präfix `mcp_secret_`.

<Request>
```http
POST /register HTTP/1.1
Host: mcp.nomadfiling.com
Content-Type: application/json

{
  "redirect_uris": [
    "https://studio.acme.dev/oauth/callback"
  ],
  "client_name": "Acme MCP Studio",
  "grant_types": [
    "authorization_code",
    "refresh_token"
  ],
  "token_endpoint_auth_method": "none"
}
```
</Request>

<Response tabs="201,400">
```json
{
  "client_id": "mcp_client_l5M8wP2qX9nR4dKsV1tYgA",
  "client_id_issued_at": 1734567890,
  "redirect_uris": [
    "https://studio.acme.dev/oauth/callback"
  ],
  "grant_types": [
    "authorization_code",
    "refresh_token"
  ],
  "response_types": [
    "code"
  ],
  "token_endpoint_auth_method": "none",
  "client_name": "Acme MCP Studio"
}
```

```json
{
  "error": "invalid_redirect_uri"
}
```
</Response>

Dein Client ist bereit, wenn du eine `201`-Antwort mit `client_id` erhältst. Speichere diesen Wert, weil du ihn für jeden späteren Schritt benötigst.

  </Step>
  <Step title="Leite den Nutzer zur Autorisierung weiter" icon="arrow-right">

Sende den Nutzer zu `/authorize` mit Client-ID, Redirect-URI, Response-Typ und PKCE-Challenge. Der Server prüft den Client und gibt dann eine `302`-Weiterleitung zu `https://app.nomadfiling.com/oauth/authorize` aus, wo der Nutzer den Zustimmungsbildschirm sieht.

<CodeGroup tabs="URL,cURL">
```text
https://mcp.nomadfiling.com/authorize?client_id=mcp_client_l5M8wP2qX9nR4dKsV1tYgA&redirect_uri=https%3A%2F%2Fstudio.acme.dev%2Foauth%2Fcallback&response_type=code&state=st_9dQ1vH7kLm2p&code_challenge=Q8xYQ4w4L3K-2YF6V3fY4e0l6k8d5pP1h2rS7tN9uA0&code_challenge_method=S256&scope=mcp
```

```bash
curl -i "https://mcp.nomadfiling.com/authorize?client_id=mcp_client_l5M8wP2qX9nR4dKsV1tYgA&redirect_uri=https%3A%2F%2Fstudio.acme.dev%2Foauth%2Fcallback&response_type=code&state=st_9dQ1vH7kLm2p&code_challenge=Q8xYQ4w4L3K-2YF6V3fY4e0l6k8d5pP1h2rS7tN9uA0&code_challenge_method=S256&scope=mcp"
```
</CodeGroup>

Nach der Freigabe sendet die App ein POST an `/approve`, erstellt einen Autorisierungscode mit dem Präfix `mcp_code_` und leitet den Nutzer mit den Query-Parametern `code` und `state` zu deiner `redirect_uri` zurück.

  </Step>
  <Step title="Tausche den Autorisierungscode gegen Token" icon="play-circle">

Rufe `/token` mit `grant_type=authorization_code`, dem Autorisierungscode, derselben Redirect-URI, deiner Client-ID und dem PKCE-Verifier auf, wenn der Ablauf PKCE verwendet hat. Der Server prüft den Code, markiert ihn als verwendet und gibt ein Access-Token plus ein Refresh-Token zurück.

<Request>
```http
POST /token HTTP/1.1
Host: mcp.nomadfiling.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=mcp_code_f4Qz2Lp8Rx0Nc6JvT3sWkB1HyD7MeA9U&redirect_uri=https%3A%2F%2Fstudio.acme.dev%2Foauth%2Fcallback&client_id=mcp_client_l5M8wP2qX9nR4dKsV1tYgA&code_verifier=v7mK2qN4rP8xT1sD6wZ9cL3hB5yF0jU2eA4nR7pQ1tV
```
</Request>

<Response tabs="200,400">
```json
{
  "access_token": "mcp_at_u4Nh7Lp2Qx9dWc5Tz1kRb8Vm3Ys6Pf0Ja2He9Mn4Kw",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "mcp_rt_x8Qm2Ls7Pd4Tv1Zn6Ky3Wc9Rb5Hf0Jq2Ne8Ua6Gp1Dr",
  "scope": "mcp"
}
```

```json
{
  "error": "invalid_grant"
}
```
</Response>

Dein Client ist authentifiziert, wenn du das zurückgegebene `access_token` als `Authorization: Bearer mcp_at_...` senden kannst und der MCP-Server eine `tools/call`-Anfrage akzeptiert.

  </Step>
  <Step title="Abgelaufene Zugriffstoken erneuern" icon="refresh-cw">

Rufe `/token` erneut mit `grant_type=refresh_token` und dem aktuellen Refresh-Token auf. Der Server widerruft die alte Token-Zeile und gibt ein neues Access-Token- und Refresh-Token-Paar zurück.

<Request>
```http
POST /token HTTP/1.1
Host: mcp.nomadfiling.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=mcp_rt_x8Qm2Ls7Pd4Tv1Zn6Ky3Wc9Rb5Hf0Jq2Ne8Ua6Gp1Dr
```
</Request>

<Response>
```json
{
  "access_token": "mcp_at_t6Vr3Qn8Lp1Yd5Ks9Wm2Hb7Fc4Jx0Pe6Au3Nz8Rg2Ty",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "mcp_rt_q5Lp9Xs2Nc7Wd1Tv4Kr8Hm3Jf6Py0Za2Ge5Ub1Dn8Mv",
  "scope": "mcp"
}
```
</Response>

Speichere das neue Refresh-Token sofort. Die Token-Rotation wird erzwungen, daher bleibt das vorherige Refresh-Token nach einer erfolgreichen Erneuerung nicht mehr gültig.

  </Step>
</Steps>

## Referenz zur dynamischen Client-Registrierung

Verwende `/register`, um einen Client zu erstellen, bevor du den OAuth-Ablauf startest.

### Request-Body

<ParamField body="redirect_uris" param-type="string[]" required="true">
Liste erlaubter Redirect-URIs für den Client. Der Server lehnt die Anfrage mit `invalid_redirect_uri` ab, wenn eine Redirect-URI fehlt oder ungültig ist.
</ParamField>

<ParamField body="client_name" param-type="string" required="false">
Menschenlesbarer Client-Name, der mit dem Client-Datensatz gespeichert wird.
</ParamField>

<ParamField body="grant_types" param-type="string[]" required="false">
Grant-Typen für den Client. Standard sind `authorization_code` und `refresh_token`.
</ParamField>

<ParamField body="token_endpoint_auth_method" param-type="string" required="false" enum="none,client_secret_post">
Client-Authentifizierungsmethode für den Token-Endpunkt. Standard ist `none`. Wenn `client_secret_post` gesetzt ist, erzeugt der Server ein Client-Secret und speichert nur dessen SHA-256-Hash.
</ParamField>

### Antwortfelder

<ResponseField name="client_id" field-type="string" required="true">
Client-Kennung mit dem Präfix `mcp_client_`.
</ResponseField>

<ResponseField name="client_secret" field-type="string" required="false">
Client-Secret mit dem Präfix `mcp_secret_`. Wird nur zurückgegeben, wenn `token_endpoint_auth_method` nicht `none` ist.
</ResponseField>

<ResponseField name="client_id_issued_at" field-type="integer" required="true">
Unix-Zeitstempel, wann die Client-ID ausgestellt wurde.
</ResponseField>

<ResponseField name="redirect_uris" field-type="string[]" required="true">
Registrierte Redirect-URIs für den Client.
</ResponseField>

<ResponseField name="grant_types" field-type="string[]" required="true">
Dem Client zugewiesene Grant-Typen.
</ResponseField>

<ResponseField name="response_types" field-type="string[]" required="true">
Gibt immer `code` zurück.
</ResponseField>

<ResponseField name="token_endpoint_auth_method" field-type="string" required="true">
Konfigurierte Authentifizierungsmethode für den Token-Endpunkt.
</ResponseField>

<ResponseField name="client_name" field-type="string" required="false">
Menschenlesbarer Client-Name, falls bei der Registrierung angegeben.
</ResponseField>

## Referenz zum Authorization-Endpunkt

Verwende `/authorize`, um die Client-Anfrage zu prüfen und den Nutzer in den NomadFiling-Zustimmungsablauf weiterzuleiten.

### Query-Parameter

<ParamField query="client_id" param-type="string" required="true">
Registrierte OAuth-Client-ID.
</ParamField>

<ParamField query="redirect_uri" param-type="string" required="true">
Redirect-URI, die genau mit einer der registrierten Redirect-URIs des Clients übereinstimmt.
</ParamField>

<ParamField query="response_type" param-type="string" required="true" enum="code">
Muss `code` sein.
</ParamField>

<ParamField query="state" param-type="string" required="false">
Undurchsichtiger Wert, der unverändert an deine Redirect-URI zurückgegeben wird. Verwende ihn, um CSRF zu verhindern und Browserzustand zuzuordnen.
</ParamField>

<ParamField query="code_challenge" param-type="string" required="false">
PKCE-Code-Challenge. Wenn vorhanden, erfordert der Token-Austausch einen passenden `code_verifier`.
</ParamField>

<ParamField query="code_challenge_method" param-type="string" required="false" enum="S256,plain">
PKCE-Prüfmethode. Standard ist `plain`, wenn weggelassen.
</ParamField>

<ParamField query="scope" param-type="string" required="false">
Angefragter Scope. Standard ist `mcp`.
</ParamField>

### Verhalten

Wenn die Anfrage gültig ist, gibt der Server `302 Found` zurück und leitet den Browser zu `https://app.nomadfiling.com/oauth/authorize` weiter, wobei die Anfrageparameter weitergegeben werden. Nachdem der Nutzer den Zugriff genehmigt hat, ruft die App `/approve` auf, erzeugt einen Autorisierungscode und leitet den Browser mit `code` und `state` zu deiner `redirect_uri`.

## Referenz zum Token-Endpunkt

Verwende `/token` sowohl für den Authorization-Code-Austausch als auch für die Refresh-Token-Rotation.

### Authorization-Code-Grant

<ParamField body="grant_type" param-type="string" required="true" show-location="false" enum="authorization_code">
Muss `authorization_code` sein.
</ParamField>

<ParamField body="code" param-type="string" required="true" show-location="false">
Autorisierungscode mit dem Präfix `mcp_code_`.
</ParamField>

<ParamField body="redirect_uri" param-type="string" required="true" show-location="false">
Muss mit der während der Autorisierung verwendeten und mit dem Autorisierungscode gespeicherten Redirect-URI übereinstimmen.
</ParamField>

<ParamField body="client_id" param-type="string" required="true" show-location="false">
OAuth-Client-ID, die den Code angefordert hat.
</ParamField>

<ParamField body="code_verifier" param-type="string" required="false" show-location="false">
Erforderlich, wenn die Autorisierungsanfrage `code_challenge` enthalten hat. Für `S256` hasht der Server den Verifier mit SHA-256 und vergleicht die base64url-Ausgabe mit `code_challenge`. Für `plain` muss der Verifier genau `code_challenge` entsprechen.
</ParamField>

### Refresh-Token-Grant

<ParamField body="grant_type" param-type="string" required="true" show-location="false" enum="refresh_token">
Muss `refresh_token` sein.
</ParamField>

<ParamField body="refresh_token" param-type="string" required="true" show-location="false">
Refresh-Token mit dem Präfix `mcp_rt_`.
</ParamField>

### Token-Antwortfelder

<ResponseField name="access_token" field-type="string" required="true">
Bearer-Zugriffstoken mit dem Präfix `mcp_at_`.
</ResponseField>

<ResponseField name="token_type" field-type="string" required="true">
Immer `Bearer`.
</ResponseField>

<ResponseField name="expires_in" field-type="integer" required="true">
Lebensdauer des Zugriffstokens in Sekunden. Der aktuelle Wert ist `3600`.
</ResponseField>

<ResponseField name="refresh_token" field-type="string" required="true">
Refresh-Token mit dem Präfix `mcp_rt_`.
</ResponseField>

<ResponseField name="scope" field-type="string" required="true">
Gewährter Scope. Der aktuelle Wert ist `mcp`.
</ResponseField>

### Fehler des Token-Endpunkts

| HTTP-Status | Fehler | Bedeutung |
| --- | --- | --- |
| `400` | `invalid_grant` | Autorisierungscode oder Refresh-Token fehlt, ist ungültig, abgelaufen, widerrufen, bereits verwendet oder stimmt nicht mit der Client-Anfrage überein |
| `400` | `unsupported_grant_type` | `grant_type` wird nicht unterstützt |
| `400` | `invalid_request` | Die Anfrage ist fehlerhaft oder erforderliche Parameter fehlen |
| `500` | `server_error` | Der Server ist bei der Verarbeitung der Anfrage fehlgeschlagen |

## Token-Formate und Laufzeiten

Jeder Anmeldedatentyp hat ein festes Präfix und Speichermuster. Der Server hasht Geheimnisse vor der Suche, ausgenommen Client-IDs und Autorisierungscodes.

| Token-Typ | Präfix | Rohgröße | Laufzeit | Speicherung |
| --- | --- | --- | --- | --- |
| API-Schlüssel | `nf_` | 32 Bytes, hex-kodiert | Konfigurierbar | SHA-256 in `api_keys.key_hash` |
| OAuth-Client-ID | `mcp_client_` | 16 Bytes, base64url-kodiert | Permanent | Klartext in `oauth_clients` |
| OAuth-Client-Secret | `mcp_secret_` | 32 Bytes, base64url-kodiert | Permanent | SHA-256 in `oauth_clients.client_secret_hash` |
| Autorisierungscode | `mcp_code_` | 24 Bytes, base64url-kodiert | 5 Minuten | Klartext in `oauth_auth_codes` |
| Zugriffstoken | `mcp_at_` | 32 Bytes, base64url-kodiert | 1 Stunde | SHA-256 in `oauth_tokens.access_token_hash` |
| Refresh-Token | `mcp_rt_` | 32 Bytes, base64url-kodiert | 30 Tage | SHA-256 in `oauth_tokens.refresh_token_hash` |

Alle Token werden mit `crypto.getRandomValues` und base64url-Kodierung erzeugt, außer API-Schlüsseln, die nach dem Präfix `nf_` hexadezimal angezeigt werden. Die Refresh-Token-Rotation wird erzwungen, daher widerruft jede erfolgreiche Erneuerung die vorherige Token-Zeile und stellt ein neues Token-Paar aus.

## Sicherheitshinweise

<Callout kind="danger">

Protokolliere keine Roh-Bearer-Token, Autorisierungscodes oder Client-Secrets. Protokolliere stattdessen Token-Präfixe, Request-IDs und Nutzer-IDs.

</Callout>

<Callout kind="info">

Wenn du einen öffentlichen Client baust, behandle `client_id` als öffentliche Metadaten und `code_verifier`, Zugriffstoken und Refresh-Token als Geheimnisse. Speichere Refresh-Token verschlüsselt und rotiere sie unmittelbar nach der Erneuerung.

</Callout>

## FAQ

<ExpandableGroup>
  <Expandable title="Welche MCP-Methoden erfordern Authentifizierung?" default-open="true">

`tools/call` erfordert Authentifizierung. `initialize`, `tools/list` und `ping` sind ohne Authentifizierung erlaubt.

  </Expandable>
  <Expandable title="Wann sollte ich API-Schlüssel statt OAuth verwenden?">

Verwende API-Schlüssel für private Backend-Integrationen, geplante Jobs und Skripte, die unter deiner Kontrolle laufen. Verwende OAuth, wenn Nutzer sich anmelden, Zugriff genehmigen oder dein Client erneuerbare delegierte Anmeldedaten benötigt.

  </Expandable>
  <Expandable title="Unterstützt der Server Refresh-Token-Rotation?">

Ja. Jede erfolgreiche Erneuerung widerruft die alte Token-Zeile und gibt ein neues Access-Token- und Refresh-Token-Paar zurück. Ersetze das gespeicherte Refresh-Token unmittelbar nach jeder Erneuerung.

  </Expandable>
  <Expandable title="Was verursacht invalid_grant-Fehler?">

`invalid_grant` bedeutet in der Regel, dass der Autorisierungscode oder das Refresh-Token abgelaufen, widerrufen oder bereits verwendet ist, die Hash-Suche fehlgeschlagen ist, die Client-ID nicht übereinstimmt, die Redirect-URI nicht übereinstimmt oder der PKCE-Verifier nicht zur gespeicherten Challenge passt.

  </Expandable>
  <Expandable title="Erfordert der Server PKCE?">

PKCE ist bedingt erforderlich. Wenn die Autorisierungsanfrage `code_challenge` enthalten hat, muss die Token-Anfrage einen gültigen `code_verifier` enthalten. Für öffentliche Clients verwende PKCE bei jeder Autorisierungsanfrage.

  </Expandable>
</ExpandableGroup>
